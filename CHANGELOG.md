## [Unreleased]

### Upgrade notes

- **`make verify` is now the full live verification (#416)** — the golden-only check that `make verify` ran before is now `make verify-goldens` (`make verify VERIFY_PATHS=<dirs>` on the command line still runs only those goldens, as CI does). A bare `make verify` also runs every live pytest suite and needs two dedicated, empty CUBRID databases in `CUBRID_TEST_URL` and `CUBRID_DASHBOARD_TEST_URL` besides the `make up` database; `CONTRIBUTING.md` ("Live verification") shows how to start them. Run `make deps` again first: it now installs every example's requirements and `pytest-asyncio`.
- **A local lab started from the earlier `docker-compose.yml` needs a one-time recovery (#385)** — the new lab file recreates the `cubrid-cookbook` container with a fixed host name and named volumes, and an existing database then fails to open with `-353`, because CUBRID recorded the old host name. The data is kept: `GETTING_STARTED.md` ("A lab created before the October 2026 lab fix") gives the tested recovery for a default 11.2 lab (rewrite the host in `databases.txt`, then restart) and for an 11.4 lab (copy the database from its unnamed volume into the new named volume first). Do not use `docker compose down -v` to recover; it deletes the data.

### Added
- **FastAPI quickstart `GET /health` and live CRUD tests (#420)** — `quickstart/5min-fastapi/app.py` gains `GET /health`, which runs `SELECT 1 FROM db_root` on a new connection and returns `{"status":"ok","database":"ok"}`, or HTTP `503` with `{"status":"error","database":"unavailable"}` and no error details when the database cannot be reached. The mocked suite covers both answers. The new `quickstart/5min-fastapi/tests/test_live.py` drives the app with `TestClient` against a running CUBRID named by `CUBRID_TEST_URL` and checks each answer against the table through a separate pycubrid connection: startup and `/health`, `POST /items` with the committed row, `GET /items` and `GET /items/{id}`, `404` for a missing `id`, `422` for three invalid bodies with no row written, a rejected over-long insert that leaves no row, and `503` from a real connection attempt to a closed port. `get_conn()` now passes `connect_timeout=10`, so `/health` answers `503` instead of hanging on an unreachable host. Tests write only rows marked with a random `live-qs-` prefix and delete exactly those, so repeated runs pass. `make test` leaves `test_live.py` out, so it never needs or writes to a database; run on their own, the live tests skip without `CUBRID_TEST_URL`, while a configured but unreachable database fails. `make verify-quickstart` (and the full `make verify`) runs them with `CUBRID_LIVE_GATE=1` (a missing URL also fails) and writes JUnit and a summary to `.live-evidence/quickstart/` (ignored by git). The quickstart README, its Korean page and `SUPPORT_MATRIX.md` document the endpoint and the command. CI does not run the live suite yet.
- **Release verification also runs on Python 3.11 (#238)** — `smoke-test.yml` takes the Python version from a new `python` matrix axis (`["3.12"]`). A release verification (`repository_dispatch`, a `workflow_dispatch` pinned to a package, or a `workflow_call` from a driver's release workflow) adds exactly one cell, CUBRID 11.4 on Python 3.11, the supported minimum, running the same full job (`make verify`, AI-agent, Flask/FastAPI, async-worker, Django and dashboard suites, offline guards). Push to `main`, the daily schedule and latest-release manual runs keep the two Python 3.12 cells, so no schedule and no other run costs more; the release adds one job (about the length of an 11.4 cell). The caller contract is unchanged: same inputs and outputs, the existing job names (`Smoke Tests (CUBRID 11.2)` / `(CUBRID 11.4)`) and artifact names stay, the new cell is `Smoke Tests (CUBRID 11.4, Python 3.11)` with the artifact `release-verification-part-cubrid-11.4-py3.11`. Each report `matrix` entry gains a `python` field (`scripts/release_smoke.py summary --python`), and a failure reason names the cell (`CUBRID 11.4, Python 3.11: …`); a release report now also fails unless exactly the three expected cells (`11.2`/3.12, `11.4`/3.12, `11.4`/3.11) each reported once, naming any missing, duplicate or unexpected cell, and every cell must have passed with the requested version (this also closes the earlier gap where a missing 11.2 or 11.4 part went unnoticed); non-release runs are unchanged, and the Python is left out of a cell name for the default 3.12. Job hygiene is unchanged (60-minute timeout, pinned actions, `persist-credentials: false`, `contents: read`). `tests/test_release_verification.py` and `tests/test_release_dispatch.py` fail if the extra cell is wrong or unconditional, the expected cell set drifts from the workflow matrix, a cell is missing or duplicated, the report matrix is not sorted, `summary --python` is not recorded, the Python is hard-coded again, the artifact names collide, or `inputs.` reaches a step. `CONTRIBUTING.md` and `SUPPORT_MATRIX.md` describe the cell.
- **Stricter guard tests for the driver lanes (#239, #241 review follow-up)** — `tests/test_ci_scope.py` now asserts exact lines instead of substrings: the caller's `if: github.event_name == 'schedule'`, the activity-guard comparison (`-ge "$ACTIVE_DAYS"`), `ACTIVE_DAYS: "8"`, the commit check `ok &= got == want` and the report job's default-branch clause. A new test ties the `driver-main.yml` `RECIPES` list to the directories of `scripts/driver_floors.py` `FLOOR_SETS` (parsed, not hard-coded), so both lanes cover the same recipes. The workflow comment and `CONTRIBUTING.md` document that an open tracking issue is closed only by the next run that executes, and that a manual dispatch closes it when both drivers are idle. No workflow logic changed.
- **Whole-second timestamps normalize like fractional ones (#265)** — `scripts/normalize_output.sh` now maps `{{DATE}} HH:MM:SS` and `{{DATE}}THH:MM:SS` with no fractional part to `{{DATETIME}}`, so goldens such as `fundamentals/pycubrid/09_serial_order_numbers.py` no longer fail about 1 run in 1000 when a `DATETIME` lands on `.000` and Python's `str(datetime)` drops the fraction. Values followed by a UTC offset, `Z` or an uppercase zone name (the fixed `20_timezone_datetime` outputs) stay unscrubbed, and every existing golden normalizes unchanged. `scripts/test_normalize_output.sh` covers whole-second, millisecond and microsecond variants for both separators.
- **Documented driver floors are installed and run, not only checked as text (#241)** — the new `Driver floors (CUBRID 11.4)` job in `ci.yml` runs `scripts/driver_floors.py`, which installs every documented `pycubrid`/`sqlalchemy-cubrid` floor exactly (`==`, read from the recipes' own `requirements.txt`) in one virtual environment per floor set and diffs 60 representative goldens against live CUBRID 11.4 on Python 3.12: the global floor (`pycubrid==1.6.1`, `sqlalchemy-cubrid==1.0`), the advanced SQLAlchemy floor (`1.4.2`, `fundamentals/pandas`), `fundamentals/async`, the `1.7` line (`fundamentals/connect`, `orm-basics`, `lob-handling`), the `1.9` line (`fundamentals/pycubrid`, `fundamentals/sqlalchemy`) and `fundamentals/alembic`. It is one job (about 3 minutes) selected by pull requests that change `SUPPORT_MATRIX.md`, the floor checker or lane, or a lane directory's `requirements.txt`, by the existing weekly `ci.yml` schedule and by manual `ci.yml` runs; it does not run on pushes to `main`, adds no schedule and is enforced by `CI Gate` only when selected. The golden directories without a `requirements.txt` (`fundamentals/crud`, `error-handling`, `lob-handling`, `transactions`) are now covered, and `scripts/check_dependency_floors.py` accepts extras (`sqlalchemy-cubrid[pycubrid]>=1.0`) and spaced specifiers. `tests/test_dependency_floors.py` fails when a documented floor is not installed by any floor set, a directory-specific floor runs on another directory, the lane pins drift from the requirements, or a floor change would not select the lane. **Floors raised where the lane failed:** `fundamentals/async` now needs `sqlalchemy-cubrid>=1.5` (1.4.x allows SQLAlchemy 2.1, where its async adapter calls the removed `await_` attribute; 1.5.0 is the first passing release), and `fundamentals/lob-handling` is documented as needing `pycubrid>=1.7` (1.6.x returns CLOB values with escaped newlines).
- **Startup smoke test for the root FastAPI template app (#243)** — `templates/api-service-fastapi/tests/test_root_app.py` imports the real `app.main`, runs its lifespan and checks `/health` through FastAPI's `TestClient`, using a throwaway SQLite `DATABASE_URL` so it needs no CUBRID. Previously CI only byte-compiled `app/`, so an import error or a missing dependency such as `pydantic-settings` (declared in the template's `requirements.txt` but absent from the shared smoke install list) could ship. Both the required `pytest-suites` lane in `ci.yml` (selected by any `templates/api-service-fastapi/*` change) and the non-PR `smoke-test.yml` suites now install the template's own `requirements.txt` and run this suite in its own process. `tests/test_ci_scope.py` covers the lane selection and workflow wiring. SQLite does not exercise CUBRID-specific SQL; the recipe suites continue to do that.
- **`make deps` and a time-limited, classified `make verify` (#235, #236)** — `make deps` installs `pytest`, `sqlalchemy-cubrid[pycubrid]` and the `requirements.txt` of every golden-backed example (a directory owning `expected/`) in one pip resolver call that honours `PIP_CONSTRAINT`; the discovery lives in the new `scripts/example_requirements.py`, which `scripts/release_smoke.py install-examples` now shares. It validates every path before printing any, and `make deps` fails (installing nothing) when a golden-backed `requirements.txt` path contains whitespace. `make verify` first checks that the selected examples' requirements are installed (failing once with "run `make deps` first"), then runs each script through the new portable, POSIX-only `scripts/run_example.py` (stdin from `/dev/null`, own process group; the whole group, including grandchildren, is killed on timeout, when the script exits and when the runner gets SIGINT, SIGTERM or SIGHUP; exit 124 plus a `run_example: timed out after` line on timeout; no GNU `timeout`; on a non-POSIX system it exits with "run_example.py requires POSIX process groups") under `VERIFY_TIMEOUT` seconds (default 60; the slowest golden took 7.2 s on CUBRID 11.4). Results are classified as `✓ PASS`, `✗ MISMATCH` (diff), `✗ EXEC-ERROR` (exit status and last 20 lines; 128 + N for a script killed by signal N), `⏱ TIMEOUT` (last 20 lines; only when exit 124 comes with the runner's timeout line, so a script that itself exits 124 is an `EXEC-ERROR`), `✗ NORMALIZE-ERROR`, `✗ READ-ERROR` or `? SKIP`; the summary keeps `N passed, N failed, N skipped` and adds a count per failure class, and under GitHub Actions each failure emits an `::error file=...::` annotation. `GETTING_STARTED.md`, `docs/quickstart.md` and `docs/ko/getting-started.md` now install `sqlalchemy-cubrid[pycubrid]` in section 2, list the `ai-agent` template, and verify a checkout with a Python 3.11+ venv → `make up` → `make deps` → `make verify`; CONTRIBUTING documents both targets. `tests/test_make_commands.py` covers the `make deps` file list (pip replaced by a recorder) and its whitespace failure, the timeout and each failure class, a script exiting 124, a script killed by SIGTERM (exit 143), `/dev/null` stdin, and that no script or grandchild outlives a timeout, a normal exit, or SIGTERM/SIGHUP to the runner.
- **Selectable local CUBRID version (#169)** — `CUBRID_VERSION=11.4 make up` selects the root Compose image while retaining the 11.2 default and the existing bounded readiness helper. Version-switch instructions no longer require editing YAML, a fixed sleep, or automatic volume deletion; image selection is not a database-format upgrade.
- **Advisory lane against pycubrid and sqlalchemy-cubrid `main` (#239)** — the new `.github/workflows/driver-main.yml` installs both drivers from their `main` branches (pinned to the commits resolved at the start of the run; `direct_url.json` is checked after install) together with the requirements of 15 representative golden directories, then runs `make verify` on them against live CUBRID 11.4 on Python 3.12, so a driver regression shows up before it is released instead of after. It is advisory only: the recipe job has `continue-on-error`, no pull request runs it, and `CI Gate` does not depend on it. A failure opens or updates one tracking issue (`ci: cookbook recipes failing against driver main`, label `ci`), which is closed automatically when the recipes pass again — the reporting pattern of sqlalchemy-cubrid's upstream canary. No new schedule: the existing weekly `ci.yml` schedule calls it (job `driver-main-advisory`), skipped when neither driver's `main` changed in the last 8 days, and it can be dispatched manually. It runs only in the upstream repository. `tests/test_ci_scope.py` fails if the lane joins the gate, gains its own schedule or a pull-request trigger, loses `continue-on-error`, or stops installing the drivers from their `main` commits.

This small matrix does not duplicate the full Python 3.12 smoke/framework suite, and failure, cancellation or unexpected skip blocks the CI gate.

### Changed
- **`make test` and `make verify` are the two test commands (#416)** — `make test` runs the unit and mocked suites with no database or Docker (`make test-offline` stays as an alias, and `make check` runs it). `make verify` without `VERIFY_PATHS` is now the full live verification: `scripts/live_gate.py all` first checks every database URL, server and example dependency, then runs every golden (`make verify-goldens`, the former golden-only `make verify`) and every live pytest suite in a fixed order, one at a time: the FastAPI quickstart, migration and performance on the `make up` database (`localhost:33000/testdb`, which the examples hard-code), the Flask/FastAPI, Django/Celery and AI agent suites on `CUBRID_TEST_URL`, and the dashboard on `CUBRID_DASHBOARD_TEST_URL`. Both URLs must name dedicated, empty databases, distinct from each other and from the `make up` database. It fails closed on an unreachable database, a SQLite or other non-`cubrid+pycubrid` URL, a missing dependency, a skipped or empty suite, a suite that leaves or drops tables, and a failed golden, and writes `.live-evidence/verify-summary.json` with golden and pytest results reported separately, the CUBRID server, Python and package versions and the commit. `make verify VERIFY_PATHS=<dirs>`, as CI calls it, keeps the golden-only check of those roots and now says it is partial. `make deps` installs `pytest-asyncio` (which the FastAPI recipe suites import) and every example's `requirements.txt` (golden-backed examples and the live suites) in one pip call. The live lanes added earlier in this release are now feature-named `make verify-*` targets (`verify-quickstart`, `verify-performance`, `verify-web`, `verify-django-celery`, `verify-ai-agent`, `verify-dashboard`, `verify-templates`), the gate variable is `CUBRID_LIVE_GATE` and evidence goes to `.live-evidence/<lane>/`. `make demo` runs `verify-goldens`. No workflow changed.
- **The performance benchmarks print the workload they ran (#423)** — `performance/fetch-optimization/benchmark.py` prints the rows each fetch strategy returned, `performance/bulk-insert/benchmark.py` prints a `SELECT COUNT(*)` of the rows each strategy stored (taken after its timer stops) instead of the configured count, and `performance/connection-pooling/benchmark.py` prints how many connections each strategy opened (SQLAlchemy `connect` event). Timings, strategies and table cleanup are unchanged; the three READMEs describe the new output.
- **The FastAPI and SQLAlchemy quickstart labs behave like the root lab (#386)** — `quickstart/5min-fastapi/docker-compose.yml` and `quickstart/5min-sqlalchemy/docker-compose.yml` now publish their ports on `127.0.0.1` only (the lab's `dba` account has no password), give the database container a fixed host name (`cubrid-fastapi`, `cubrid-sqlalchemy`) and keep the database in two named volumes (`cubrid_data`, `cubrid_databases`), so `docker compose down` keeps the data and only `docker compose down -v` deletes it. The FastAPI `api` service gains a health check on `/openapi.json`: without it, `docker compose up --wait` returned while Uvicorn was still starting and the first request got `Connection reset by peer`. The image (`cubrid/cubrid:11.2`), the database `testdb`, the port numbers and the apps are unchanged. A quickstart container created from the earlier files kept its data in unnamed volumes; to start clean, run `docker compose down -v` in that quickstart's folder before you update. `tests/test_quickstart_config.py` fails if a quickstart publishes a port beyond `127.0.0.1`, loses its fixed host name or a named volume, or the FastAPI API loses its health check.
- **The outbox recipe's ack and fail require the lease attempt (#339)** — in `templates/flask/08-transactional-outbox`, `POST /api/outbox/<id>/ack` and `/fail` identified the caller's lease only by `processor_id` and compared `attempts` with the value the request read, so a stale request sent after the same `processor_id` leased the message again settled the newer lease. **Request change:** both endpoints now require `lease_attempt`, the `attempts` value `/outbox/lease` returned (a missing value returns 409, a boolean or other non-integer value 400). The conditional UPDATE compares `attempts` with that value, a stale attempt returns 409 ("this lease is stale") and leaves the newer lease untouched, and `/fail` decides dead-letter versus requeue from it. New tests lease as `worker-1` (attempt 1), expire the lease, lease again as `worker-1` (attempt 2) and send the attempt-1 ack and fail (409, attempt 2 intact, no attempt row; 200 on the previous code), then settle attempt 2 normally; the in-window race test also runs with a same-processor re-lease, and a test covers the 400 cases. The recipe README documents the request body.
- **Docs-sync allowlist entries must record a reason (#174)** — `scripts/check_docs_sync.py` `load_allowlist()` used to drop everything after `#` and keep the path, so an entry with no reason (`performance/foo`) was silently accepted although `scripts/docs-sync-allowlist.txt` asks for one. It now follows `scripts/check_expected_coverage.py`: blank lines and full-line `#` comments are still ignored, `path  # reason` is accepted (the reason may contain further `#`), and an entry without a reason or with an empty one raises an error naming the file and line, which makes the gate exit 1 instead of reporting success. `tests/test_docs_sync.py` covers each case, the non-zero exit and the repository's own allowlist; the allowlist header and `CONTRIBUTING.md` state the rule.
- **Compose files drop the obsolete `version` key (#173)** — the root `docker-compose.yml`, `quickstart/5min-fastapi/docker-compose.yml`, `quickstart/5min-sqlalchemy/docker-compose.yml` and `templates/api-service-fastapi/docker-compose.yml` no longer start with `version: "3.8"` / `"3.9"`. Compose v2 ignores the key and warns that it is obsolete; `docker compose config` now prints no warning. Services, images, ports and volumes are unchanged.
- **Flask recipes 02 and 07 get their own table names (#277)** — Flask 02 (`02-categories`) now creates `cookbook_flask_categories` (its self-referencing and product `ForeignKey` strings follow) instead of `cookbook_categories`, which the root FastAPI template app keeps, and Flask 07 (`07-vendor-feed`) now creates `cookbook_feed_products` instead of `cookbook_products`, which Flask 01 keeps. No recipe shares a table with another any more, so the FastAPI root app with Flask 02, and Flask 01 with Flask 07, can run their live-CUBRID suites concurrently against one instance. Routes and API responses are unchanged. A database created by an earlier version keeps the old tables; the two recipes create new ones, so drop the old Flask 02 and Flask 07 tables by hand if they are no longer needed. `KNOWN_SHARED` in `tests/test_table_prefix.py` is now empty, so the guard is a strict no-sharing check across recipes; `SUPPORT_MATRIX.md` drops the sequential-run advice for these suites (the dashboard suite still needs its own database because it reuses `cookbook_products`).
- **FastAPI recipes 09-12 and Flask recipes 09-11 prefix their tables with `cookbook_` (#139)** — the 23 tables these seven recipes created without a prefix (`orders`, `users`, `roles`, `documents`, `inventory_items`, …) are now `cookbook_<name>`, with the 12 matching `ForeignKey` strings, as `AGENTS.md` and `CONTRIBUTING.md` already required. Generic names could collide with a reader's own tables. `inventory_items` was shared by FastAPI recipe 09 and Flask recipe 11, so FastAPI 09 now uses the distinct `cookbook_saga_inventory_items` (Flask 11 keeps `cookbook_inventory_items`), and likewise `cookbook_saga_orders` (FastAPI 09) and `cookbook_rbac_documents` (Flask 09) avoid the names FastAPI 02 and FastAPI 07 use and their live-CUBRID suites can run concurrently against one instance. Routes, URL paths and API responses are unchanged. A database created by an earlier version keeps its old tables; the renamed recipes simply create new ones, so drop the old tables by hand if they are no longer needed. The new `tests/test_table_prefix.py` (in `make test-offline`) fails when any `__tablename__` or `Table("…")` in `templates/**/models.py` lacks the prefix or when a new table name is declared by two recipes. `templates/ai-agent/` (`agent_*`, `rag_*`, `chat_*` tables, with a test and README that name them) is left for a separate change.

- **Release verification waits until PyPI serves the requested version (design C4)** — before installing `package==version` for a release request (`repository_dispatch`, a pinned `workflow_dispatch` or a `workflow_call`), `scripts/release_smoke.py select` now polls the PyPI JSON API (`https://pypi.org/pypi/<package>/<version>/json`, anonymous) until it lists exactly that version with a wheel or sdist, with 5/10/20/30 s backoff inside a 600 s wall-clock budget. HTTP and network errors, malformed JSON, another version or a release without files count as not yet served; on timeout the job fails with `PyPI does not serve <package>==<version> after N s (<last reason>)`, where the reason names the HTTP/JSON error or what PyPI served instead (`served <name> <version> with N wheel/sdist files`, to diagnose stale CDN nodes), and never falls back to another version.
