# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- **Selectable local CUBRID version (#169)** — `CUBRID_VERSION=11.4 make up` selects the root Compose image while retaining the 11.2 default and the existing bounded readiness helper. Version-switch instructions no longer require editing YAML, a fixed sleep, or automatic volume deletion; image selection is not a database-format upgrade.
- **Representative Python compatibility matrix (#130)** — required PR/main CI checks Python 3.11–3.14 on CUBRID 11.4 using the existing read-only pycubrid connection and SQLAlchemy engine/session goldens, plus imports and source compilation. This small matrix does not duplicate the full Python 3.12 smoke/framework suite, and failure, cancellation or unexpected skip blocks the CI gate.
- **Offline contributor command** — `make check` combines lint, documentation, normalizer, golden-coverage, and isolated offline regression suites; `make test-offline` runs the suites without a database. CI uses the same command, and both live smoke jobs run the Make/readiness guards before driver selection.
- **AI agent template (#111)** — `templates/ai-agent/` with 5 examples: agent state management (sessions, messages, tool calls with JSON columns), MCP tool chain (programmatic server invocation), RAG metadata hybrid (document store with SET tagging + SEQUENCE chunk tracking), agent loop (query → think → act → observe), and AI chatbot backend (SQLAlchemy ORM with JSON LLM I/O). Requires `cubrid-mcp-server>=0.3`.
- **One-command dashboard demo** — `templates/dashboard/` now ships its own `docker-compose.yml` (CUBRID **11.4** + Streamlit at http://localhost:8501), and the five recipes read `DATABASE_URL` from the environment (default unchanged: `cubrid+pycubrid://dba@localhost:33000/testdb`) so the compose service can point them at the co-located container.
- **Streamlit dashboard pytest suite (#103)** — `templates/dashboard/tests/test_dashboard.py` uses `streamlit.testing.v1.AppTest` to exercise all 5 dashboard recipes: a parametrized smoke test that every recipe runs without raising, plus assertions that the seeded table viewer renders rows, the KPI page's four metric cards are non-empty, and narrowing the category filter shrinks the rendered dataframe. The suite runs against a live CUBRID instance when `CUBRID_TEST_URL` is set and otherwise falls back to a shared SQLite file for local/offline runs; `conftest.py` makes the recipes' CUBRID/MySQL-style `AUTO_INCREMENT` DDL SQLite-compatible via a dialect-gated SQLAlchemy event hook, without changing the recipes themselves, and drops the demo tables in FK-safe order before and after the session. `SUPPORT_MATRIX.md`'s "Streamlit templates" row moves from "manual run" to this pytest suite. This replaces the unwired, CWD-relative `tests/test_dashboard.py` added by #120.
- **Gate the Streamlit dashboard pytest suite in CI (#142)** — Every pull request runs `templates/dashboard/tests` in its own required live-CUBRID **11.4** job, separate from the Flask/FastAPI database. On pushes to `main`, nightly, and manual smoke runs, each existing **11.2/11.4** matrix job first finishes the Flask/FastAPI suites, then stops their container and runs the dashboard suite in a separate disposable CUBRID container of the same version. This removes the shared-schema FK failure (`cookbook_sales` references `cookbook_products`) without deleting another recipe's tables or relying on suite order. The dashboard's own fixture still drops its tables in FK-safe order, and its SQLite-only `AUTO_INCREMENT` hook is scoped to its test URL and removed even when teardown fails. `SUPPORT_MATRIX.md` and `docs/index.md` describe the trigger-specific coverage and isolation.
- **Live async-worker database task checks (#129)** — `templates/async-worker/tests` invokes the existing sales aggregation, report, and batch email tasks directly without Redis, then confirms CUBRID persisted their job states, JSON results, reports, and email logs. The suite requires an empty dedicated database, fails on a configured connection error or preexisting worker tables, and removes only its own tables. A separate required CUBRID 11.4 PR job and the non-PR 11.2/11.4 smoke matrix gate this database path; broker delivery and Celery's result backend remain manual coverage.
- **Live Django SQLAlchemy-bridge checks (#128)** — `templates/django/tests` exercises the existing Django HTTP `/health` and `/items` views against CUBRID, then updates and deletes the persisted row through the template's SQLAlchemy bridge. It does not add a native Django CUBRID backend, ORM model, or migration. The suite rejects non-CUBRID or unreachable configured URLs and preexisting `cookbook_items`, cleans up only its own table, and runs in a separate required CUBRID 11.4 PR job plus the non-PR 11.2/11.4 smoke matrix after colliding examples.

### Changed
- **Least-privilege workflow tokens and no persisted checkout credentials (#237)** — `ci.yml` now declares top-level `permissions: contents: read`; the reusable `doc-lint` call explicitly grants the `contents: read` and `pull-requests: read` that workflow declares. Every `actions/checkout` step in every workflow sets `persist-credentials: false`. The Dependabot auto-merge job now also requires `github.event.pull_request.user.login == 'dependabot[bot]'` (not only the actor) and holds its `contents: write` / `pull-requests: write` grants at job level only. `tests/test_workflow_permissions.py` (in `make test-offline`) fails if a workflow loses its top-level permissions, a checkout persists credentials outside the push allowlist, or the auto-merge guard weakens. The repository's default workflow permissions setting is unchanged and remains a maintainer decision.
- **Tiered CI validation; no duplicate PR live matrices (#222)** — the new `scripts/ci_scope.py` classifies every `ci.yml` run from its event and changed paths, and the live CUBRID lanes now start only when selected: docs-only pull requests start no live CUBRID; a recipe pull request runs only its family's live lane (the representative Flask/FastAPI `01-basic-crud` suites, dashboard, async-worker, Django, CQRS) on CUBRID 11.4 / Python 3.12; golden examples and AI-agent changes run `make verify` scoped to the touched examples. Shared live infrastructure (`Makefile`, Compose, normalizer, readiness/coverage scripts) and CI-policy changes fan out to every lane, CUBRID 11.2 + 11.4 and the Python 3.11/3.14 endpoints; changes to `fundamentals/pycubrid` or `fundamentals/sqlalchemy` add the endpoints; recipe 10's `requirements.txt` runs CQRS on both versions. Pushes to `main`, a new weekly schedule and manual `ci.yml` runs keep Python 3.11–3.14 and CQRS on 11.2 + 11.4. `smoke-test.yml` no longer runs on pull requests: the PR golden/AI-agent/MCP smoke moved into two `ci.yml` jobs (shared steps in `.github/actions/pr-smoke`) that keep the required check names `Smoke Tests (CUBRID 11.2)` and `Smoke Tests (CUBRID 11.4)`, so branch protection is unchanged and a skipped lane reports *skipped*. `smoke-test.yml` keeps the broad push/nightly 11.2/11.4 run and its exact release verification inputs, outputs and fail-closed reporting; the daily schedule stays because 10 of 37 recent scheduled runs caught `make verify` failures, mostly on days without a `main` push. The cubrid-mcp-server tool-contract smoke moved verbatim into `scripts/mcp_smoke.py`, shared by both workflows. `CI Gate (all checks must pass)` is a fail-closed allow-list: a lane may be skipped only when the classifier output for it is exactly `false`; a failure, cancellation, unexpected skip or failed classification fails it. `tests/test_ci_scope.py` (run by `make check`) covers the classifier, the gate and the workflow wiring. Measured on real runs and the last 40 merged pull requests: a docs-only PR goes from 21 jobs (12 live) / ~24 billed minutes to 10 jobs (0 live) / ~10, a Dependabot recipe bump to 11 jobs (2 live) / ~11, and the 40-PR total from ~960 to ~734 billed minutes; `CONTRIBUTING.md` "CI tiers" has the full table and `SUPPORT_MATRIX.md` now states which tier/event backs each "CI-verified" claim. Dependabot grouping is unchanged.
- **CODEOWNERS routing for high-blast-radius surfaces (#223)** — new `.github/CODEOWNERS` routes review of workflows (including the reusable `smoke-test.yml` release verification contract), `dependabot.yml`, `SECURITY.md` and shared validation/golden infrastructure (`Makefile`, `scripts/`, `tests/`) to the maintainers; recipes are intentionally unowned and the file is routing only, not a security boundary. `SECURITY.md` gains a durable supported-versions statement and notes that private vulnerability reporting is not enabled (email remains the private route). Repository settings are unchanged.
- **Python 3.11 or later required (#220)** — Python 3.10 reached upstream end of life on 2026-10-01, so the cookbook's current support range is now **3.11–3.14**: the README badge and prerequisites, `SUPPORT_MATRIX.md`, `CONTRIBUTING.md`, `llms.txt` and recipe READMEs say 3.11+, Ruff targets `py311`, and Python 3.10 is removed from the required representative compatibility matrix (no jobs were added; real-query/golden checks continue on 3.11–3.14). **Migration:** Python 3.10 users need an older compatible cookbook/driver combination (earlier cookbook commits and the `pycubrid`/`sqlalchemy-cubrid` releases they pin) or must upgrade Python. Standalone recipe `requirements.txt` files were audited and contain no explicit Python 3.10 constraints; framework and driver floors are unchanged, and teaching examples were not rewritten for 3.11 syntax. Historical entries and measurements are preserved.
- **Recipe dependency floors aligned with the documented support contract (#152)** — several standalone `requirements.txt` files pinned `pycubrid` well below the documented `SUPPORT_MATRIX.md` floor (`migration/java-to-python`, `quickstart/5min-fastapi` at `>=0.5`; two FastAPI recipes at `>=0.2.6`; `fundamentals/pandas`, `fundamentals/sqlalchemy`, `templates/dashboard`, `templates/django` at `>=1.3.2`; `fundamentals/isolation-levels`, `alembic`, `json`, `async` and `pitfalls/reserved-words` at the stale `>=1.6.0`), and `quickstart/5min-sqlalchemy` left both drivers unbounded. Every standalone FastAPI and Flask recipe `requirements.txt` (`templates/api-service-fastapi/recipes/*`, `templates/flask/*`) also listed `pycubrid`/`sqlalchemy-cubrid` with no version at all, even though each recipe installs its own `requirements.txt` independently per its README. All of these now pin the documented floor for their category: the global minimum (`pycubrid>=1.6.1`, `sqlalchemy-cubrid>=1.0`), the `>=1.4.2` advanced-SQLAlchemy floor, or the `>=1.7,<2`/`>=1.8,<2` per-recipe/per-template exceptions already in `SUPPORT_MATRIX.md` — which now also documents the `templates/` family's `>=1.7,<2` convention explicitly. The new `scripts/check_dependency_floors.py` (run by `make check`) fails on a bare driver requirement, a floor below its documented minimum, or an undocumented custom pin, so this can't silently drift again; `tests/test_dependency_floors.py` covers it. CONTRIBUTING documents the policy. Release-smoke VCS/direct-URL contamination is unaffected: it is already handled separately by the existing driver-selection guard (#147/#161, documented in CONTRIBUTING's "Release smoke dependencies").
- **Dependabot version updates configured; workflow actions aligned (#153)** — `dependabot-auto-merge.yml` existed without any `.github/dependabot.yml`, so no scheduled version updates were ever opened. The new config checks GitHub Actions weekly (one grouped PR) and every standalone recipe `requirements.txt` monthly, grouped by dependency name so a package bump is one PR across all recipes rather than one per recipe directory; CUBRID driver major updates are ignored because their floors are the `SUPPORT_MATRIX.md` contract, and `versioning-strategy: increase-if-necessary` keeps Dependabot from raising a recipe's own floor on a minor/patch bump when the existing range already allows the new version. PR titles and squash commits use the `chore(deps):` prefix, and the existing auto-merge workflow (patch/minor only, gated on the required checks) is unchanged. `ci.yml`, `smoke-test.yml` and `docs-sync.yml` now use the same `actions/checkout` v7.0.1 and `actions/setup-python` v7.0.0 SHA pins as `docs.yml` (previously v4.4.0/v5.6.0 there). `tests/test_dependabot_config.py` (run by `make check`) fails when a recipe `requirements.txt` falls outside the configured directories, the commit prefix changes, the pip versioning strategy changes, or an action is not SHA-pinned or pinned to different versions across workflows. CONTRIBUTING documents the dependency maintenance policy.
- **Unified issue, pull request and commit titles** — `CONTRIBUTING.md` now defines the cubrid-lab title rule (`type(scope)!: description` with `feat`, `fix`, `docs`, `test`, `perf`, `refactor`, `ci`, `build`, `chore`, `style`, `revert`; no bracket prefixes or issue numbers), and `AGENTS.md`, the pull request template and both issue forms point to it. The issue forms now prefill `fix: ` (bug report) and `feat: ` (example request) instead of `[Bug]: ` and `[Example]: `. The new unprivileged `PR title` workflow (`.github/workflows/pr-title.yml`) checks every pull request title, and `tests/test_pr_title.py` (run by `make test-offline`) exercises its embedded validator.
- **Manual release smoke runs pin the requested release (#177)** — `smoke-test.yml`'s `workflow_dispatch` now takes `package` (`latest`, `pycubrid`, `sqlalchemy-cubrid`, `cubrid-mcp-server`) and `version` (`MAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH`) inputs. `scripts/release_smoke.py` reads them from the event JSON and routes a pinned manual run through the same exact PyPI install, bounded retry, constraint pinning, package-index origin check and job summary as an upstream `repository_dispatch`, so the upstream `RELEASING.md` fallback (`gh workflow run smoke-test.yml -R cubrid-lab/cubrid-cookbook-python -f package=<package> -f version=<X.Y.Z>`) verifies the exact release instead of floating latest. Invalid or unavailable requests fail; a manual run with default inputs keeps the ordinary latest-release smoke behavior and is reported as not a release verification.
- **Release verification runs are identified by request id and report the installed version (#187)** — `smoke-test.yml` accepts an optional `request_id` (`^[A-Za-z0-9._-]{8,80}$`) in the `repository_dispatch` payload and as a `workflow_dispatch` input, read and validated from the event JSON by `scripts/release_smoke.py`. A release verification run is named `Release verification <package>@<version> [request_id=<id>]`, so the upstream release workflows (cubrid-lab/pycubrid#539) can find exactly their run through the Actions API, and the request id joins the non-cancelling concurrency group. A new `Release verification report` job combines both CUBRID jobs into a job summary, step outputs and a `release-verification-<request_id>` artifact (`release-verification.json`, schema version 1: requested and installed version, status, reasons, run and per-job details) and fails when a job failed or installed a different version. The contract is documented in CONTRIBUTING; the bounded publication retry and the no-fallback rule are unchanged.
- **Package release workflows can call the smoke test without a token (#190)** — `smoke-test.yml` now also runs on `workflow_call`, so the release workflows in `pycubrid`, `sqlalchemy-cubrid` and `cubrid-mcp-server` can run it as a job with their own `GITHUB_TOKEN` (`uses: cubrid-lab/cubrid-cookbook-python/.github/workflows/smoke-test.yml@<sha>`; inputs `package`, `version`, `request_id`; outputs `status`, `requested_version`, `installed_version`, `artifact`) instead of a cross-repository dispatch token. Each job detects the call (`job.workflow_ref` differs from the caller's `github.workflow_ref`), checks out `cubrid-lab/cubrid-cookbook-python` at the called workflow's own commit, and `scripts/release_smoke.py` reads the call inputs from `RELEASE_INPUT_*` environment variables instead of the caller's event JSON, with the same exact-install, bounded-retry, no-fallback and requested == installed rules. Release verification concurrency groups now also include the run, so a called run never shares or cancels the caller's group. `repository_dispatch` and `workflow_dispatch` are unchanged; the call contract is documented in CONTRIBUTING.
- **Release smoke verifications are no longer cancelled by other runs (#177)** — `smoke-test.yml`'s concurrency group now includes the event name, requested package and version/ref, and `cancel-in-progress` is off for release verifications (`repository_dispatch`, or `workflow_dispatch` with a non-`latest` package), so a push to `main` or a second release no longer cancels an in-flight release check. Push, PR, schedule and unpinned manual runs still cancel superseded runs of the same kind.
- **Removed stale nested Flask recipe copies (#136)** — deleted the seven duplicated `01-basic-crud` directories from the category templates while retaining the canonical `templates/flask/01-basic-crud/` recipe. Thanks @jackgedge.
- **`batch-etl` quiets Alembic's plugin-discovery logging** — `templates/batch-etl/04_etl_pipeline.py` configures the root logger at INFO. `sqlalchemy-cubrid` 1.8.0 (#504) imports its Alembic `DefaultImpl` when the CUBRID dialect loads and Alembic is installed, and Alembic >=1.18 logs `setup plugin ...` at INFO from `alembic.runtime.plugins` on import — noise from Alembic's own plugin discovery, not the recipe's ETL output, that only surfaces when Alembic happens to be installed alongside this example (e.g. the full `make verify` / smoke-test run, which also installs `fundamentals/alembic`'s requirements into the same environment). `configure_logging()` now sets the `alembic` logger to `WARNING` after `basicConfig()` so the recipe's own INFO lines stay unaffected. The golden output is unchanged; `batch-etl` is the only template that configures INFO-level root logging via `logging.basicConfig`, so no other recipe is affected.
- **pycubrid 1.8.0 goldens** — `fundamentals/pycubrid/16_batch_error_handling` now expects no exception-detail suffix: pycubrid 1.8.0 keeps `errno` on batch errors (#390), so `str(exc)` ends with `(errno=-670, description=..., sqlstate='23000')`, which the existing normalizer rule strips (1.7.x printed only `(sqlstate='23000')`). `fundamentals/pycubrid/20_timezone_datetime` now expects DATETIMELTZ in the pinned `Asia/Seoul` session zone (`+09:00`, same instants): pycubrid 1.8.0 keeps the CAS session across `commit()` (#468/#472), whereas 1.7.x reconnected on commit and the read ran in a fresh UTC session. The recipe's comments that described UTC-aware LTZ reads as driver behavior are corrected. These goldens assume pycubrid >= 1.8.0, so `fundamentals/pycubrid/requirements.txt` is raised from `pycubrid>=1.7,<2` to `pycubrid>=1.8,<2` (documented consistently in its README and `SUPPORT_MATRIX.md`); `fundamentals/connect` and `fundamentals/orm-basics` keep `pycubrid>=1.7,<2`, since their goldens do not depend on either behavior.
